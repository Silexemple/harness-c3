# Harness "cable" protocol — ESP32 dial ⇄ PC daemon over USB Serial/JTAG

Complete specification of the wire protocol between a Harness dial (ESP32, "device"/"dial") and the
Harness daemon running on the computer it is plugged into ("daemon"/"host"), reconstructed from
`autonomous-ai/openharness` (MIT). The repo contains **no** `docs/specs/cable-protocol.md` (it is
referenced in comments but not committed); this document is rebuilt from the two normative
implementations and their shared test vectors:

Every field name below was checked against the source. Ambiguities are marked `// TODO-VERIFY`.

**Target reimplementation note (ESP32-C3):** the reference device is an ESP32-S3 (native USB
Serial/JTAG peripheral, USB VID:PID `303a:1001`). The ESP32-C3 has the same ROM USB-Serial-JTAG
peripheral and enumerates with the same `303a:1001` identity, so the framing, vocabulary and
daemon behaviour apply unchanged. The USB identity cannot be changed (ROM descriptor), which is
deliberate — see §10.

## 1. Transport

- **Physical:** the SoC's built-in USB Serial/JTAG (CDC-ACM) peripheral. USB VID `0x303a`,
  PID `0x1001`. This is the board's ONLY USB port and is shared with the ESP console (ROM boot
  log, second-stage bootloader, panic handler all write plain text to it).
- **Daemon port discovery** (`serial.ts`): match on USB VID/PID only, never on device-node name.
  - macOS: `ioreg -p IOService -w0 -l`, arm the subtree at the node carrying
    `idVendor=0x303a` + `idProduct=0x1001`, take the first `IOCalloutDevice` (`/dev/cu.usbmodem*`).
  - Linux: scan `/sys/class/tty/ttyACM*` and `ttyUSB*`, walk up to 4 parent levels to find
    `idVendor`/`idProduct`, use `/dev/<name>`.
- **Port settings:** raw mode, no line discipline: `stty -f/-F <path> raw clocal -echo -echoe
  -echok -echoctl -echoke min 1 time 0`. Opened with `O_RDWR | O_NOCTTY | O_NONBLOCK`
  (`O_NOCTTY` is load-bearing: without it unplugging the cable SIGHUPs and kills the daemon).
  Baud rate is meaningless on USB-CDC; none is set.
- **Byte stream, not message-oriented.** Both sides run a reassembling decoder (§2.3).

## 2. Binary framing

### 2.1 Frame layout

Little-endian throughout:

```
offset  size  field
0       2     magic: 0xA5 0x48          ('H' = Harness; see §10.1)
2       1     version: u8 = 1           (CABLE_FRAME_VERSION — the ENVELOPE version)
3       1     type: u8                  (see §2.2)
4       2     len: u16 LE               payload length in bytes
6       len   payload
6+len   2     crc16: u16 LE
```

- Header = 6 bytes (`CABLE_HEADER_BYTES`), CRC = 2 bytes.
- `CABLE_MAX_PAYLOAD = 8192`. A sender MUST refuse to encode a larger payload (treated as a bug,
  never truncated). `CABLE_MAX_FRAME = 6 + 8192 + 2 = 8200`.
- **CRC-16/CCITT-FALSE**: poly `0x1021`, init `0xFFFF`, no reflection, no final XOR.
  Check value for ASCII `"123456789"` is `0x29B1` (asserted by both test suites and by the
  vector generator).
- **CRC coverage: bytes 2..(6+len-1), i.e. `ver | type | len | payload`. The magic is NOT
  covered** (it is a constant marker; covering it would detect nothing).
- CRC is transmitted little-endian (low byte first).

Worked example (from the vectors): payload `{}`, type JSON:

```
A5 48 01 01 02 00 7B 7D 10 77
│  │  │  │  │     │  │  └─┴─ crc16 = 0x7710 (LE)
│  │  │  │  └─┴── len = 2
│  │  │  └─────── type = 0x01 (JSON)
│  │  └────────── version = 1
└──┴───────────── magic
```

### 2.2 Payload types

| type | name | direction | payload |
|---|---|---|---|
| `0x01` | JSON | both | one UTF-8 JSON object with a `"t"` discriminator (the vocabulary, §3–§6) |
| `0x02` | PCM | device → daemon only | one chunk of raw 16-bit mono PCM during a voice turn (§8) |
| `0x03` | FW | daemon → device only | one slice of a firmware image (§7) |
| `0x04` | LOG | device → daemon only | one ESP_LOG line, raw bytes (no JSON escaping), trailing `\r\n` stripped (§9) |

An **unknown type code is NOT dropped by the framing layer**: it is handed up with its raw byte so
a newer peer reads as a visible mismatch. The device's message layer counts it (`unknown`); the
daemon logs `cable: unknown frame type 0x..`.

### 2.3 Decoder / resync rules (both sides implement the identical algorithm)

The decoder keeps a fixed buffer of `CABLE_MAX_FRAME` (8200) bytes and two counters:
`discardedBytes` and `corruptFrames`. Feed bytes; emit complete frames in order. **It never
fails and never throws**: any byte that makes no sense is stepped over. Rules, in order:

1. If the buffer is full and still no frame decoded, discard the oldest 1 byte (keeps the link
   alive; refusing the new byte would wedge permanently).
2. Attempt decode only once ≥ 6 bytes are buffered (magic scan is amortised: it runs on resync,
   not per byte).
3. If the head is not magic: scan for the next `A5 48` pair, **stopping one short of the end**
   (a trailing lone `0xA5` is kept — its second byte may not have arrived yet). Discard everything
   before the pair (counted as `discardedBytes`).
4. If `len > 8192`, the two "length" bytes were noise: discard exactly **1 byte**, keep scanning.
5. Wait until the whole frame (`6 + len + 2`) is buffered.
6. CRC mismatch: increment `corruptFrames`, discard exactly **1 byte** (NOT the whole candidate —
   the magic may be a coincidence inside noise and a genuine frame may start one byte later), keep
   scanning.
7. On success: emit `{version, type, payload}` (payload copied out, not a view), consume the frame,
   immediately try again (one read can complete several frames).
8. `reset()` on port (re)open drops a partial frame but deliberately **keeps the counters** — their
   trend across a run is the diagnostic (a handful of discards per boot = bootloader text, expected;
   a steady trickle mid-session = format disagreement or bad cable).

The exhaustive decoder contract (including expected counter values per noise pattern) is the vector
file `cable_frame.txt` shipped beside this document. Your ESP32-C3 implementation MUST pass the
`encode` and `stream` cases in it; `gen_cable_vectors.py --check` regenerates/verifies it.

## 3. Session & handshake

Over a cable there is no connection to lose: the daemon quitting and the daemon having nothing to
say are both silence. So liveness is entirely cadence-based.

### 3.1 Timing constants

| Constant | Value | Side | Meaning |
|---|---|---|---|
| `HELLO_ALONE_MS` | 2000 ms | device | no session: greet every 2 s (the daemon cannot see the dial until it speaks) |
| `HELLO_SESSION_MS` | 15000 ms | device | session up: keepalive + re-introduction in case the daemon restarted inside the silence window |
| `SILENCE_MS` | 15000 ms | device | nothing of ANY kind for 15 s → session down (`session_down("silence")`) |
| `PING_EVERY_MS` | 5000 ms | daemon | send `{"t":"ping"}` every 5 s while the port is open |
| `SILENCE_MS` | 20000 ms | daemon | no bytes for 20 s → close and reopen the port (deliberately longer than the device's 15 s so one late message cannot trip both sides at once) |
| `REOPEN_EVERY_MS` | 2000 ms | daemon | min interval between port-open attempts |
| `OPEN_TIMEOUT_MS` | 20000 ms | daemon | one port-open attempt may take at most 20 s (raised from 8 s after measured ~9.6 s opens on a post-flash re-enumeration) |
| `FOREIGN_AFTER_MS` | 12000 ms | daemon | bytes but zero decodable frames for 12 s → the port is another product's dial; release it |
| foreign retry | 60000 ms | daemon | don't re-probe a port written off as foreign for 60 s |
| tick | 1000 ms | daemon | session housekeeping interval |
| device session loop | 250 ms | device | `session_task` period (checks silence + hello cadence) |

### 3.2 `hello` (device → daemon, JSON 0x01)

Sent immediately at boot and then on the cadence above. Exact fields, in construction order
(`cable_client.c send_hello()`):

```json
{
  "t": "hello",
  "fw": "0.0.86",
  "product": "harness",
  "proto": 3,
  "hw": "cst9217+axp2101",
  "mac": "28:84:85:90:5F:78"
}
```

| field | type | meaning |
|---|---|---|
| `t` | string | `"hello"` |
| `fw` | string | firmware version **read from the RUNNING image** (`esp_app_get_description()->version`), never a constant — the daemon's offer decision compares this string, and two sources cannot be kept equal. `version.txt` of the reference tree: `0.0.86`. Dev builds self-describe as e.g. `v0.3.38-36-gbc64073-dirty` (ESP-IDF `git describe`). |
| `product` | string | MUST be exactly `"harness"` (`CABLE_PRODUCT`). **Positive match: absence or any other value means "foreign"**, never "probably ours". A non-matching greeting gets NO `welcome`; the daemon releases the port and retries it no sooner than 60 s later. |
| `proto` | number | message-vocabulary version, `CABLE_PROTO_VERSION = 3`. History (from comments): proto 1 put the dial's own MAC where `welcome.machine.id` now is; proto 2 changed that to the cabled computer's real machine id and fixed the `answer` shape; proto 3 added `question.close`. The envelope version (frame byte 2) is separate and stays 1. |
| `hw` | string | which of the dial board variants this is, self-detected at boot: `"cst9217+axp2101"`, `"cst816s"`, `"cst816s+axp2101"`. Informational; a daemon that predates the field ignores it. // TODO-VERIFY: exact set of values a C3 build should report — the reference boards are S3-based; pick a distinct name and expect the daemon to merely log it. |
| `mac` | string | WiFi STA MAC, uppercase, colon-separated (`esp_read_mac(..., ESP_MAC_WIFI_STA)`, `%02X:...`). Also the device's USB serial number, so the daemon can distinguish dials before any exchange and tell a keepalive from a new board. |

### 3.3 `welcome` (daemon → device, JSON 0x01)

EVERY `hello` is answered. Only a dial that is new OR came back on a different fw version gets the
full state push afterwards (otherwise a 15-second keepalive would re-send everything forever).

Exact shape (`cableSession.ts` hello handler):

```json
{
  "t": "welcome",
  "proto": 3,
  "app": "harness",
  "machine": { "id": "mac-local", "name": "MacBook Pro" },
  "selected": "mac-local",
  "voiceLang": "en"
}
```

| field | type | meaning |
|---|---|---|
| `proto` | number | daemon's vocabulary version |
| `app` | string | daemon app name (`host.appName()`; `"harness"` in the reference host) |
| `machine.id` | string | the CABLED computer's identity: its real backend machineId, or a `cable:<computerId>` placeholder when signed out. This is what the device judges `local` rows against and what selecting the local row sends back. |
| `machine.name` | string | that computer's display name |
| `selected` | string | the machine id the agent list currently belongs to. Stated up front so the ✓ is right from the first frame (matters after a dial reboot mid-session on a remote selection). The device falls back to `machine.id` when empty. |
| `voiceLang` | string | a PROPOSAL (`"en"`/`"vi"` from the daemon's locale). The device keeps its own choice in NVS and states it on every `voice.begin`. |

Device behaviour on `welcome` (`session_up`): stores machine name/id, marks the UI connected,
enables framed logging (§9), and — only on the FIRST welcome of a session — sends
`machines.list` and `agents.list` explicitly (a rebooted dial greets with the same mac/fw, which
the daemon would otherwise read as a keepalive and push nothing), then replays `last_words`.

### 3.4 Keepalive

- Daemon → device: `{"t":"ping"}` every 5 s.
- Device → daemon: `{"t":"pong"}` in reply to each ping (no fields).
- The device's 15 s `SILENCE_MS` is refreshed by ANY inbound frame (any type), so the ping cadence
  alone holds the session up. Daemon-side, any BYTE refreshes `lastRx`; 20 s of silence closes and
  reopens the port (the read on a dead `/dev/cu.usbmodem*` handle never completes and never raises,
  so silence is the only detectable symptom).

### 3.5 Attach push order (daemon → device, after a new/changed hello)

Asserted verbatim by `cableSession.spec.ts`:

```
welcome → machines.begin → machine ×N → machines.end → swarms → agents.begin → agent ×M → agents.end → notif.replace
```

Machines FIRST (the dial paints its eyebrow from the machine list), swarms before agents (the tab
name should not lag the tiles), `notif.replace` LAST (it names agents the carousel must already
hold). History restore (`summary` with `restore:true`, §5.16) follows in the background, off the
critical path.

### 3.6 Session down (device side)

On 15 s silence: forget ALL agents and machines (a tile is a claim that something is running right
now), keep the last selected machine id (a session that comes back on the same computer should land
where it was), restore the plain console (log framing off), abort any firmware transfer
(`fw_update_abort("session down")`), UI shows "Not connected".

## 4. Messages: device → daemon

All are JSON frames (type 0x01) unless noted. Payloads are compact UTF-8 JSON; strings MUST be
properly JSON-escaped (agent names and spoken sentences carry quotes/backslashes/newlines). The
device caps one JSON message at 2048 bytes on receive; keep outbound messages comfortably small.

Field-presence conventions used throughout: **omitted means "no value"** — an empty string is never
sent where absence carries meaning (notably `voice.begin.agentId`), and absent boolean flags read as
`false` so an older peer behaves exactly as before.

### 4.1 `hello` — handshake, see §3.2.

### 4.2 `pong`
```json
{"t":"pong"}
```
Reply to `ping`. No fields.

### 4.3 `agents.list`
```json
{"t":"agents.list"}
```
Ask for the agent list (streamed back as `agents.begin`/`agent`×N/`agents.end`). Sent right after
the first `welcome`, and spontaneously whenever the device receives an `agent.updated` it wants
reconciled (the cheapest correct answer to "one agent changed" is to re-ask).

### 4.4 `machines.list`
```json
{"t":"machines.list"}
```
Ask for the machine wheel (`machines.begin`/`machine`×N/`machines.end`). Sent right after the first
`welcome`.

### 4.5 `machine.select`
```json
{"t":"machine.select","machineId":"m2"}
```
The user tapped a machine row. **ALWAYS answered** — `machine.selected` or `machine.error`, never
silence, because the dial holds a spinner until one lands. A select of the already-selected machine
is answered with `machine.selected` too (silence would read as a hang).

### 4.6 `swarms.list`
```json
{"t":"swarms.list"}
```
Re-ask for the window's swarm list (a screen that just opened wants it fresh).

### 4.7 `swarm.select`
```json
{"t":"swarm.select","swarmId":"s2"}
```
The user tapped a swarm (tab). NOT answered directly: the window switches, and the next `swarms` +
agent-list push IS the answer. Selecting an unknown id is dropped by the daemon with a log line.
`swarmId` is a 32-hex-char desk id; the device buffer is 48 bytes (`SWARM_ID_MAX = ID_MAX = 48`) —
a 32-byte buffer truncated ids to 31 chars and every pick missed ("ignored select for unknown
swarm").

### 4.8 `turn.send`
```json
{"t":"turn.send","agentId":"a1","text":"fix the login screen"}
```
Deliver user text into an agent. Fire-and-forget: outcomes arrive as unsolicited
`turn.started`/`turn.done`/`summary`/`turn.error`. Daemon drops it unless both fields are non-empty
strings.

### 4.9 `turn.stop`
```json
{"t":"turn.stop","agentId":"a1"}
```
Interrupt that agent's running turn, and only that one.

### 4.10 `focus`
```json
{"t":"focus","agentId":"a1"}
```
The carousel settled on this tile. A statement about where the user is LOOKING, not a request to run
anything; debounced by the caller. The daemon forwards it to the desktop window, records it as the
single shared `desiredFocus`, and may suppress it during app-driven switch repaint windows
(`APP_FOCUS_SETTLE_MS = 750` ms echo window, `APP_SWITCH_REPAINT_MS = 1000` ms repaint window).

### 4.11 `agent.open`
```json
{"t":"agent.open","agentId":"a2","reason":"question"}
```
"Put this one in front of me" — a notification was tapped, or a question screen came up on its own.
Different verb from `focus`: asks the window for a tile of this agent's own. `reason` is ABSENT for
a person's tap (an older daemon reads the frame exactly as before); the only defined value is
`"question"`, for which the window only brings the agent forward if already on screen (a reconnect
re-shows every unanswered question, and each used to open a tab).

### 4.12 `agent.fork`
```json
{"t":"agent.fork","agentId":"a2"}
```
Ask for a fork of the agent (a second agent with its history, opened in the window). The daemon
answers a refusal as a `toast` carrying `detail ?? error`. // TODO-VERIFY: the CURRENT reference
firmware never sends this (the vocabulary rule says all construction lives in `cable_client.c`, and
no `agent.fork` builder exists there; the fork UI was removed — `ui_screens.c:8697`). The daemon
handler is live, so a C3 firmware MAY send it; expect only a toast on failure, silence on success.

### 4.13 `scroll`
```json
{"t":"scroll","phase":"move","dy":12}
{"t":"scroll","phase":"up","dy":3,"v":-1800}
```
The dial is a touchpad for the computer's window; it reports MOVEMENT, not position (it cannot know
the terminal's height — the side that owns the scrollback does the arithmetic). Fields:

| field | type | meaning |
|---|---|---|
| `phase` | string | `"down"` (finger landed — stops any coasting fling), `"move"` (travelled `dy` device px since last report, positive = down the glass), `"up"` (finger lifted) |
| `dy` | number | travel in device pixels since the last report; may be 0 — **a zero `dy` is never elided**: a bare `down` stops a fling, a bare `up` is a finger that came to rest and must land as a stop, not a throw |
| `v` | number | velocity in device px/s, signed like `dy`, sent ONLY on `up`; becomes the fling |

The daemon drops a stroke whose phase is not one of the three.

### 4.14 `answer`
```json
{"t":"answer","agentId":"a1","requestId":"q1","answers":{"Which DB should I use?":"Postgres"}}
```
Answer to a `question`. `requestId` is the daemon's opaque id echoed byte-for-byte. `answers` is the
UI's own object, one string entry PER QUESTION, keyed by the exact `key`s the daemon asked with —
it travels verbatim (re-deriving it, or keying it by requestId, is how a rename becomes an answer
nobody gave; the proto-1 daemon demanded `{id, optionId}` and silently dropped every real answer).
Values: the chosen option label(s) — multi-select joins labels with `", "` — or a spoken-answer
transcript. Non-string values are dropped by the daemon.

### 4.15 `models.list` — THE ONLY ROUND TRIP
```json
{"t":"models.list","agentId":"a1","mode":"model","selected":"runtime-v1:s1:claude:opus@high"}
```
Ask for one agent's runtime model/effort catalog. Everything else in this protocol is
fire-and-forget; the picker is the exception because there is nothing to draw until the catalog
arrives. Fields: `agentId` (required), `mode` (optional, `"model"` or `"effort"` — which chip was
tapped), `selected` (optional, the current opaque profile id). The device blocks a NON-UI task
(never the LVGL task) up to `MODELS_WAIT_MS = 4000` ms for the `models` reply; the daemon ALWAYS
answers, with `items: []` on error or empty catalog (silence would strand the picker on a spinner).

### 4.16 `agent.update`
```json
{"t":"agent.update","agentId":"a1","model":"opus","effort":"high"}
```
Runtime model/effort chosen on the tile's chips. `model` and `effort` are plain words (not the
opaque `runtime-v1:` profile); each is omitted when empty. The daemon owns what they mean for its
engine.

### 4.17 `voice.begin`
```json
{"t":"voice.begin","agentId":"a1","cmd":"goal","lang":"en","sr":16000}
```
Start a voice turn. Fields:

| field | presence | meaning |
|---|---|---|
| `agentId` | **OMITTED entirely when there is no agent** (never `""`) — absence tells the daemon it must route the transcript itself | the tile the user was on |
| `cmd` | omitted when none | command word: `"goal"` or `"loop"` in the reference firmware; the daemon prepends it as `/<cmd> <transcript>` |
| `lang` | always | capture language, from device NVS; default `"en"` |
| `sr` | always (number) | PCM sample rate. The daemon states it to the transcriber; a `voice.begin` without `sr` (older firmware) is assumed `16000`. Device: `AUDIO_SAMPLE_RATE = 16000`, 16-bit mono. |

Followed by PCM frames (§8), then `voice.end` or `voice.abort`.

### 4.18 `voice.end`
```json
{"t":"voice.end"}
```
Utterance complete; the daemon transcribes and routes (§8).

### 4.19 `voice.abort`
```json
{"t":"voice.abort","why":"cable stalled"}
```
Abandon the capture; the daemon discards all buffered PCM. `why` optional (observed values:
`"cable stalled"`, `"aborted"`).

### 4.20 `voice.confirm`
```json
{"t":"voice.confirm","routeId":"r123","agentId":"a1"}
```
Answer to a `voice.transcript` that arrived with `needsConfirm: true`: the user confirmed the
routing. The daemon currently just focuses that agent. **Forward-compat path**: the current daemon
only ever sends `needsConfirm: false` (§5.21), so this is exercised by no shipping peer —
implement it, but expect it to be cold.

### 4.21 `fw.accept`
```json
{"t":"fw.accept"}
```
The device has erased its OTA slot and is expecting bytes; nothing is sent before this. See §7.

### 4.22 `fw.progress`
```json
{"t":"fw.progress","written":8192}
```
Sent after EVERY slice written to flash (`PROGRESS_EVERY = 1`). `written` is the CUMULATIVE byte
count in flash. This is not only a progress bar — it is the ACK that opens the daemon's credit
window (§7.3).

### 4.23 `fw.done`
```json
{"t":"fw.done"}
```
Image complete, SHA-256 verified against the offer, boot partition set; the device reboots ~400 ms
later (the delay lets the frame reach the daemon before the USB link vanishes — a device that
disappears mid-sentence reads as a crash, not a success).

### 4.24 `fw.error`
```json
{"t":"fw.error","message":"sha256 mismatch"}
```
The transfer failed; the running image is untouched. Observed `message` values (device,
`fw_update.c`): `"more bytes than the offer promised"`, `"flash write failed"`, `"image rejected by
esp_ota_end"`, `"sha256 mismatch"`, `"could not set the boot partition"`. Declining an offer is NOT
one of these — declining is silence, and the daemon offers again on the next `hello`.

## 5. Messages: daemon → device

Inbound JSON handling on the device (`cable_client.c handle_message`): the payload object may nest
its fields under a `"p"` member, but flat messages are equally legal (`p` is a convenience, not a
requirement — the device falls back to the root object). A message without `t` is counted `bad`;
an unknown `t` is counted `unknown` and ignored, never fatal.

### 5.1 `welcome` — see §3.3.

### 5.2 `ping`
```json
{"t":"ping"}
```
Every 5 s while the port is open. Answer with `pong`.

### 5.3 `agents.begin`
```json
{"t":"agents.begin"}
```
Start of the STREAMED agent list: reset the staged list. (The list is streamed — begin, one message
per agent, end — because a frame is capped at 8 KB and a hundred agents do not fit; one agent per
message bounds message length by construction.)

### 5.4 `agent` (one row of the streamed list)
```json
{"t":"agent","id":"a1","name":"Fix login screen","engine":"claude","model":"opus","effort":"high","machineId":"mac-local","machine":"MacBook Pro"}
```
| field | notes |
|---|---|
| `id` | required; rows with a missing/empty id are dropped. Device cap `ID_MAX = 48` (uuid or 32-hex + NUL). |
| `name` | falls back to `id` when empty. Cap `NAME_MAX = 40`. |
| `engine` | e.g. `claude`, `codex`, `cursor`, `opencode`; `""` when the daemon did not say. Device buffer 12 bytes. |
| `model`, `effort` | plain words for the tile's chips (the device reassembles them into the opaque `runtime-v1:<id>:<engine>:<model>@<effort>` profile the UI reads; a model with no effort axis gets `"auto"`). Device buffers 24/16 bytes. |
| `machineId`, `machine` | where the agent lives: the id is what the device sends back for EVERY action (turn/stop/answer routing), the name is drawn under the agent's. `""` from a daemon that predates the fields; every reader falls back. |

The daemon sends all fields always (empty-string-filled). The device holds at most
`CABLE_MAX_AGENTS = 16` rows — the list is the window's ACTIVE TAB and nothing else.

### 5.5 `agents.end`
```json
{"t":"agents.end","total":22,"tab":"t1"}
```
End of the streamed list; the UI rebuilds tiles. `total` = account-wide agent count (the Overview
prints this; the rows behind it stay on the daemon). `tab` = active tab's id, `""` when no window is
open — that is how an empty list reads as "the app is shut" rather than "this tab is empty"
(different screens: "Run OpenHarness on your computer" vs "Nothing on this tab").

### 5.6 `machines.begin` / `machine` / `machines.end`
```json
{"t":"machines.begin"}
{"t":"machine","id":"mac-local","name":"MacBook Pro","state":"ready","local":true}
{"t":"machines.end","selected":"mac-local","source":"backend"}
```
The machine wheel, streamed like the agent list. `state` is the ONLY liveness word on the wire, one
tri-value-plus-one rather than an `online` boolean beside a `known` one (one field cannot
contradict itself; two would):

| `state` | meaning |
|---|---|
| `ready` | reachable now (the LOCAL row is always `ready` — the cable is the evidence) |
| `offline` | known but not reachable |
| `unknown` | the list itself is stale |
| `needs-link` | reachable, but this daemon holds no pinned key for it, so nothing can be read |

`local` (bool): exactly one row carries `true` — the computer at the other end of the cable.
`machines.end.selected`: which machine the agent list belongs to. `machines.end.source` explains a
short list (one row with no explanation reads as "you own one machine"): `"backend"` (full fleet),
`"local"`, `"signed-out"`. Device caps: `CABLE_MAX_MACHINES = 10`, id 48, name 40, state 12 bytes.

The device gates on an actual change (hash of rows + selection) BEFORE taking any display lock; an
unchanged list costs a memcmp, not a rebuild.

### 5.7 `machine.updated`
```json
{"t":"machine.updated","id":"m2","name":"Office PC","state":"offline","local":false}
```
One row changed (liveness, rename) — cheaper than re-streaming the wheel.

### 5.8 `machine.selected`
```json
{"t":"machine.selected","machineId":"m2"}
```
Ack for `machine.select` (also sent when the selected machine was re-selected). The ONLY writer of
the device's selection state — a tap marks a row pending and waits for this; an optimistic write is
how the ✓, the Overview eyebrow and the voice gate end up disagreeing after a refusal.

### 5.9 `machine.error`
```json
{"t":"machine.error","machineId":"m2","code":"NEEDS_LINK","message":"Run harness link import"}
```
Refusal of `machine.select`. The daemon owns the code set; `message` is shown VERBATIM (no
device-side table, which would go stale the first time a code is added). Known codes
(`deviceFleet.ts` / `cableHost.ts`): `UNKNOWN_MACHINE` ("That machine is not on your account"),
`NEEDS_LINK` ("Link <name> to this computer first"), `NOT_YOURS`, `BILLING`, `UNREACHABLE`,
`UNAVAILABLE` (signed out: "Sign in on this computer to reach other machines").

### 5.10 `models` — answer to `models.list`
```json
{"t":"models","agentId":"a1","items":[{"id":"runtime-v1:s1:claude:opus@high"},{"id":"runtime-v1:s1:claude:sonnet@low"}]}
```
`items[].id` is a full opaque `runtime-v1:<sid>:<engine>:<model>@<effort>` profile string (device
buffer 192 bytes); the UI groups by model + effort. ALWAYS sent, with `items: []` on error/empty.

### 5.11 `swarms`
```json
{"t":"swarms","selected":"s1","items":[{"id":"s1","name":"Workshop","agents":2,"panes":2},{"id":"s2","name":"Launch","agents":0,"panes":0}]}
```
The window's swarms (tabs), ONE frame (not streamed: two dozen rows fit in a kilobyte), whole list
replaced on arrival. `selected` = the tab on screen. Per item: `id` (32-hex, required — rows without
are dropped), `name` (optional, `""` allowed — the window's default is "New swarm"), `agents` =
agent count, `panes` = tile count of any kind (agents, shells, viewers). `panes` is ABSENT from an
older daemon: fall back to `agents`, which is what the row meant before tiles were counted
separately (a tab with a terminal and no agent has `agents:0, panes:1`, and the difference is what
keeps it in the switcher). No window → empty `items` and the tile draws no swarm line. Device cap:
`SWARMS_MAX = 24`.

### 5.12 `focus`
```json
{"t":"focus","agentId":"a1"}
```
The daemon's surface moved (user clicked in the desktop window) — the dial should centre that tile.
Sent only for an agent the just-pushed list contains; the daemon also re-asserts it after every
agent-list push that changes shape. A focus for an unknown id lands on nothing (the device holds the
frame briefly, then drops it).

### 5.13 `turn.started`
```json
{"t":"turn.started","agentId":"a1","text":"Working…"}
```
A turn started in that agent — UNSOLICITED, including turns started at the keyboard. `text` is the
status line the tile draws ("Working…", the tool running, what it waits on). Dropping it leaves a
live turn with nothing on screen, which reads exactly like the turn never started. Device maps it to
tile kind `"processing"` (busy state on, spinner/status row).

### 5.14 `turn.done`
```json
{"t":"turn.done","agentId":"a1"}
```
Stops the spinner (tile kind `"done"`). Deliberately does NOT ring or notify: completion is
announced by the `summary` that follows. An empty/phantom turn emits only `done` — so a session
that briefly registers and vanishes stays silent.

### 5.15 `turn.error`
```json
{"t":"turn.error","agentId":"a1","message":"…"}
```
Stops the spinner AND shows `message` as a toast.

### 5.16 `summary`
```json
{"t":"summary","agentId":"a2","name":"Device firmware voice","engine":"codex","machine":"","recap":"recap two","text":"body two"}
{"t":"summary","agentId":"a1","recap":"recap one","text":"body one","quiet":true}
{"t":"summary","agentId":"a1","recap":"r","text":"t","restore":true}
```
A finished turn's recap — the tile's main readable content (tile kind `"summary"`, neutral colour).
Fields:

| field | meaning |
|---|---|
| `agentId` | target tile |
| `name`, `engine`, `machine` | WHO it is about, riding on the frame because the dial holds one tab's agents and the turn may have finished on any of them. Filled by the daemon's `describe()`; empty strings for an id it never listed. Sent on every card, not only off-tab ones, so a tab switch mid-flight cannot strand a card with an id and no name. |
| `recap` | short line (the drawer's and tile's headline) |
| `text` | full text (the reader screen) |
| `restore` | `true` = HISTORY, not news: reattach/reboot refill. No beep, no notification, no busy state. Absent = false. Sent oldest-first on attach only. |
| `quiet` | `true` = the desktop window already has this agent on screen: redraw the tile, SKIP the notification drawer — the beep still sounds. ABSENT (not false) on the ordinary path so older firmware notifies as it always did. |
| `silent` | `true` = a sub-agent's turn: redraw the tile, skip the beep AND the drawer. Absent = false. |

The completion beep and the drawer notification hang off the SUMMARY, never the bare `done`.

### 5.17 `notif.replace`
```json
{"t":"notif.replace","items":[{"agentId":"a1","name":"Fix login screen","machine":"MacBook Pro","summary":"…","question":false}]}
```
The window's whole unread list, replayed — sent once per attach (a dial that has just greeted is
known to have an empty drawer; its rows live in RAM). Max 8 items. Per item: `agentId` (required),
`name`, `machine`, `summary` (for a finished turn the last recap, filled by the daemon; for a
question the question's own first text — the dial cannot supply either after a reboot), `question`
(bool: blocked on an answer vs finished turn).

### 5.18 `notif.seen`
```json
{"t":"notif.seen","agentId":"a1"}
```
The window looked at this agent — drop its drawer row on the dial. Fire-and-forget; a dial that
predates it counts it as unknown and drops it.

### 5.19 `question`
```json
{"t":"question","agentId":"a1","name":"Fix login screen","engine":"claude","machine":"MacBook Pro","id":"q1","questions":[{"key":"Which DB should I use?","q":"Which DB should I use?","options":["Postgres","SQLite"],"multi":false}]}
```
An agent stopped to ask (AskUserQuestion). Fields: `agentId`, `name`/`engine`/`machine` (same "who
it is about" rationale as `summary`), `id` = the opaque request id the device echoes back as
`requestId` in `answer`, `questions` = array of up to (device) 4 items, each:

| field | meaning |
|---|---|
| `key` | the answer-map key, echoed back untouched in `answers` (shaped by the daemon from the engine's `prompt`/`question`/`id`/`header`) |
| `q` | the prompt text |
| `options` | array of option labels (device keeps at most 6, 80 chars each); chosen label(s) are sent back verbatim |
| `multi` | true = multi-select (toggle + Done; labels joined with `", "`) |

The device dedups on `id` (streaming + complete paths share the requestId), wakes the screen,
beeps, shows the question screen, and sends `agent.open` with `reason:"question"`. A question is a
job, not news: it is counted as unread until ANSWERED, unconditionally (no `quiet`).

### 5.20 `question.close` (proto ≥ 3)
```json
{"t":"question.close","agentId":"a1","id":"q1"}
```
That question is no longer waiting — answered in the app or in the pane by hand. This is the ONLY
way the dial learns the thing it is offering options for has been dealt with. Carries `id` so a dial
showing a DIFFERENT question cannot be closed by a stale message.

### 5.21 `voice.transcript`
```json
{"t":"voice.transcript","routeId":"","text":"fix the login screen","agentId":"a1","agentName":"Fix login screen","needsConfirm":false}
```
(example is the exact shape the daemon builds in `cableSession.ts finishVoice()`). Result of a
finished voice turn. Fields: `routeId` (routing correlation id; the current daemon always sends
`""`), `text` (the transcript), `agentId` (where the words went; may be absent when unrouted),
`agentName` (only a name the DIAL's own list knows — it draws this), `needsConfirm` (bool; when
true the device should confirm with `voice.confirm` — the current daemon always sends `false`;
// TODO-VERIFY: no shipping daemon exercises the true path), `confidence` (number, read by the
device if present; the current daemon never sends it and the device defaults to 1.0). The device drops the "sending" overlay on this message; its own watchdog
(`VOICE_ROUTE_WAIT_MS = 60000` ms) releases the overlay if neither this nor `voice.error` arrives.

### 5.22 `voice.error`
```json
{"t":"voice.error","message":"Didn't catch that"}
```
Voice turn failed; `message` is shown as a toast and releases the routing overlay. Observed daemon
messages: `"Didn't catch that"` (empty audio/transcript), the transcriber's error text,
`"Cancelled in the window"`, `"Still waiting on the window"`, `"No agent to send that to"`.

### 5.23 `toast`
```json
{"t":"toast","text":"Wait for it to finish, then fork."}
```
Show a transient toast (also how an `agent.fork` refusal surfaces).

### 5.24 `fw.offer`
```json
{"t":"fw.offer","version":"9.9.9","size":3091648,"sha256":"<64 lowercase hex chars>"}
```
Firmware update negotiation, see §7.

### 5.25 `agent.updated` — RESERVED
Handled by the device (it re-asks `agents.list`) but **never sent by the current daemon** (no
sender exists in `cableSession.ts`). // TODO-VERIFY: forward-compat hook; treat as "re-fetch the

## 6. Agent / tile state machine (what the UI expects)

The wire does not carry an agent "status" enum. Tile state is DERIVED from the message kinds above
(`ui_screens.c project_apply_event`). The device-side kinds and their rendering:

| tile kind | entered by | rendering |
|---|---|---|
| idle / resting | initial; after `ui_project_clear_event` | resting placeholder text, no card |
| `processing` (busy) | `turn.started` (also a remote `processing` event, e.g. `"Waiting for your answer"` while a question is open) | blinking-dots busy row (3 dots, ~3 Hz), status text from `turn.started.text`, red STOP affordance, counted in the Overview "N working" line |
| `done` | `turn.done` (and `turn.error`) | busy off; green `✓` marker colour if a card follows |
| `summary` | `summary` | neutral recap card; beep + drawer notification unless `silent`/`quiet`/`restore` (§5.16) |
| question pending | `question` | question screen takes the face; unread badge stays until ANSWERED (not merely seen); cleared by `answer` (locally) or `question.close` |

Notes:
- `done` with absent/empty/`"done"` text draws no card; a `summary` always carries the readable
  content.
- Busy is bounded by the device's own busy-timeout watchdog, so an abandoned question cannot pin a
  tile forever.
- Machine rows have their own tri-state: `ready` / `offline` / `unknown` / `needs-link` (§5.6).

## 7. Firmware update (OTA over the cable)

The dial has no WiFi in the cable design; the daemon reads the SAME published manifest the device
used to poll (`harness/esp32/ota/metadata.json` on GCS, key `"commander"`, fields
`{version,url,sha256,size}`), caches the image (verified against size+sha256 on EVERY load), and
offers it over the wire.

### 7.1 Offer negotiation

1. On every `hello`, the daemon computes `firmwareFor(runningFw)` → `{version, image, sha256}` or
   null. Offer gate (`shouldOffer`): both versions must match `^v?(\d+)\.(\d+)\.(\d+)$` and the
   published one must be **strictly newer**. A dev build (`git describe` string like
   `v0.3.38-36-gbc64073-dirty`) never parses → never offered. Equal is nothing to do; older is a
   rollback decided by publishing, not by whichever daemon is plugged in.
2. Anti-loop guards (daemon): each `<mac>:<version>` is offered at most once per port session AND at
   most once ever per daemon run (`written` set survives the port — every accepted flash ends in a
   reboot that starts a new session); at most `FW_WRITES_PER_HOUR = 3` writes per dial per hour.
3. Daemon sends `fw.offer` `{version, size, sha256}` (sha256 = 64 lowercase hex chars of the whole
   image).
4. Device accepts ONLY if (`fw_update_offer`): no transfer already active; `version` and
   `sha256_hex` (exactly 64 chars) and `size > 0` present; **no voice turn in flight** (a reboot
   mid-turn loses the thread and looks like a crash — the daemon re-offers on the next hello, 15 s
   away); an OTA slot exists and `slot.size >= size`. On accept it shows the OTA screen BEFORE the
   erase (which takes seconds), calls `esp_ota_begin` (this ERASES the slot — why failed offers must
   not be retried on a cadence), then sends `fw.accept`.
5. Declining = silence (no message). The daemon offers again on the next `hello` (subject to the
   guards).

### 7.2 Slices (frame type 0x03, daemon → device only)

- Payload = the next `FW_SLICE_BYTES = 8192` raw bytes of the image (last slice short). **No offset,
  no index, no per-slice hash** — slices are strictly sequential and the position is implicit.
- The device writes each slice straight to flash ON THE USB READER TASK (`esp_ota_write`), which
  blocks that task ~16 ms per slice. This is deliberate and is what the credit window is sized
  against.

### 7.3 Flow control — the credit window (the three numbers are ONE decision)

The ESP32 USB-Serial/JTAG peripheral has **NO back-pressure**: the driver ISR drains the hardware
FIFO unconditionally and silently drops whatever does not fit its ring buffer — no NAK, no short
write, the host never learns. Measured by the sibling firmware: with a smaller ring a transfer died
at 0 of 1,342,160 bytes written.

- Daemon: at most `FW_WINDOW_BYTES = 16384` (16 KB) unacknowledged in flight
  (`offset - acked < FW_WINDOW_BYTES`). `fw.progress.written` IS the credit.
- Device: acks EVERY slice (`fw.progress {written: <cumulative>}`) after `esp_ota_write` succeeds.
  Acking less often stalls the transfer; a larger slice would overrun the ring.
- Device RX ring: `USJ_RX_BUF = 32768` (32 KB) = the 16 KB window twice over, for scheduling jitter
  (~16 KB arrives at USB full speed during one 16 ms flash write). **On an ESP32-C3 port: keep RX
  ring ≥ 32 KB and slice ack-per-write.** Device TX buffer is 2048 (sized for one PCM chunk + frame).
- Daemon `pump()` is re-entrant by design (the ack arrives DURING a parked write); correctness
  requires: advance the offset BEFORE awaiting the write, and single-flight the pump loop — a
  duplicated slice once produced a perfect byte count with slice 130 sitting where 131 belonged,
  failing only at `esp_ota_end`.

### 7.4 Completion & verification

When `written == size`:
1. `esp_ota_end` (image structure check).
2. **SHA-256 of what is ACTUALLY IN FLASH** — the partition is read back in 1024-byte chunks and
   hashed, compared (lowercase hex) to the offer's `sha256`. Not a hash of bytes as they went past:
   the point is to catch a write that did not land.
3. `esp_ota_set_boot_partition`.
4. `fw.done`, render the "restarting" screen, wait 400 ms, `esp_restart()`.

Any failure → `fw.error {message}` (values in §4.24), slot aborted, UI back to projects, running
image untouched. Session loss mid-transfer → `fw_update_abort`, same safety. On the next boot the
new image must call the equivalent of `esp_ota_mark_app_valid_cancel_rollback()` (the reference does
it from `fw_mark_valid` when the running partition is `ESP_OTA_IMG_PENDING_VERIFY`). The daemon
treats `fw.done` as "installed — the dial is rebooting"; the proof is the next `hello` carrying the
new `fw` string.

## 8. Voice

- `voice.begin` → PCM frames (type 0x02) → `voice.end` (or `voice.abort`).
- PCM: raw 16-bit signed little-endian mono, at the `sr` declared in `voice.begin` (reference:
  16000 Hz). Chunk size `CABLE_VOICE_CHUNK = 1024` bytes per 0x02 frame (never larger; the device's
  TX buffer is 2048).
- Daemon cap: `VOICE_MAX_BYTES = 10 × 60 × 32000` bytes (≈10 min at 16 kHz 16-bit ≈ 32 KB/s); over
  the cap the turn is dropped with a log line.
- If a PCM write fails (host not reading), the device aborts the utterance
  (`voice.abort {why:"cable stalled"}`).
- Routing when `voice.begin` omitted `agentId`: the daemon offers the transcript to the desktop
  window's palette FIRST (`routeInWindow`, 2 s "taken" ack budget, 60 s answer budget —
  `ANSWER_MS` is deliberately the device's own `VOICE_ROUTE_WAIT_MS = 60000`), then falls back to a
  local scorer. `sent`/`cancelled`/`abandoned`/`unavailable` outcomes map to
  `voice.transcript`/`voice.error` as in §5.21–§5.22. If `cmd` was set, the daemon prepends
  `/<cmd> ` to the delivered text.
- The daemon transcribes (it owns the cloud credential; the device holds none).

## 9. Logs (frame type 0x04, device → daemon)

- The device's one USB port is shared with its console, so once a session is up the firmware hooks
  `esp_log_set_vprintf` and sends every `ESP_LOGx` line as a LOG frame: raw bytes, one line per
  frame, trailing `\r\n` stripped (the frame IS the line), lines truncated to 512 bytes rather than
  split.
- Log framing is enabled ONLY after the first `welcome` and disabled on session down (unplugged, the
  port stays an ordinary console and `idf.py monitor` works as always). A log line never becomes
  back-pressure: the sink waits at most 5 ms (`LOG_WRITE_WAIT_MS`) vs 100 ms for real messages;
  failure falls back to the plain console.
- ISR context and panic/early-boot output do NOT go through the hook (a mutex would abort); that
  text arrives as bare bytes and the daemon's decoder steps over it (counted as discarded).
- Each line is also appended to an RTC ring (`last_words`); after an abnormal reset the first
  session replays the tail of the previous boot's log as framed LOG lines, plus
  `reset reason: ...`. A 60 s `alive up=<s> heap=...` heartbeat line is printed by the display task;
  the daemon watches for it and marks gaps ≥ 90 s in the log file.
- The daemon files LOG frames (plus its own `cable:` events prefixed `[daemon]`) into
  `~/.harness/logs/dial-YYYYMMDD.log`, retaining 7 days, capping each day at 20 MB.

## 10. Known pitfalls (paid for on real hardware)

1. **The second magic byte names the product.** `0xA5 0x48` (`'H'`) is Harness; the sibling product
   ships the SAME board with the same unchangeable USB identity (`303a:1001`) and a protocol
   descended from the same ancestor, and its updater flashes any panel whose version differs from
   its bundled one — in EITHER direction. Different magic makes the two mutually unintelligible at
   the first byte pair: the sibling can never read a `hello`, never learns a version, never offers.
   `0xA5` leads because it is outside ASCII (bootloader text shares the wire). Changing one product's
   byte without the other is a link that opens and delivers nothing. The `product:"harness"` field in
   `hello` is the SECOND lock (positive match; absence means no), surviving any future re-unification
   of the magic.
2. **Shared console.** Every boot walks the decoder into the middle of ROM/bootloader/panic text.
   Hence: magic scan, CRC gate, one-byte-step resync, `len > 8192` = noise, and counters
   (`discardedBytes`, `corruptFrames`) whose RATE is the diagnostic — a handful of discards per boot
   is expected, a steady trickle mid-session means format disagreement or a bad cable.
3. **Never interleave bytes of two frames.** A frame split by a second sender is unrecoverable (both
   halves have valid magic, neither a valid CRC). Device: one TX mutex around encode+write. Daemon:
   a serialised write queue, and a `pushChain` serialising streamed begin/rows/end pushes (a dial
   that greets and asks both lists otherwise receives `begin, begin, rows, end, end`).
4. **No back-pressure on USB-Serial-JTAG** — see §7.3. RX ring sizing and the 16 KB credit window
   change together or not at all.
5. **Dead tty handles never raise** (macOS hands back the same `/dev/cu.usbmodem*` node after a dial
   reboot; writes succeed, reads never complete). Hence the daemon's 5 s ping / 20 s silence reopen.
6. **`O_NOCTTY`** or unplugging SIGHUP-kills the daemon. Raw mode or CR→NL mapping and echo mangle
   frames indistinguishably from a bad cable.
7. **Two readers on one tty shred the stream** (five readers measured costing 18 of 22 greetings).
   Hence the daemon's single-open guard with a 20 s open timeout, and the foreign-port verdict
   (bytes but zero frames for 12 s → release, retry in 60 s).
8. **Answer every `hello`, re-attach only for a dial not already greeted** (else full state every
   15 s); but a rebooted dial greets with the same mac/fw, so the DEVICE explicitly re-asks
   `machines.list` + `agents.list` after the first `welcome`.
9. **Keepalive asymmetry**: device silence window 15 s < daemon's 20 s, so one late message cannot
   make both sides conclude the other left.
10. **Version strings must come from the running image** (`esp_app_get_description()->version`), or
    self-update loops forever. Version compare is strict-semver-newer only; dev builds are never
    touched.
11. **Ack every firmware slice**, cumulatively; the ack is flow-control credit, not telemetry.
12. **`answers` is keyed by the daemon's own question keys** and travels verbatim; the proto-1
    `{id, optionId}` expectation silently dropped every answer.
13. **Omit-vs-empty matters**: `voice.begin` without `agentId` = route it yourself; `""` would read
    as "this agent". `quiet`/`silent`/`restore` are absent-not-false so older firmware behaves as
    before. `swarms` `panes` absent = fall back to `agents`.
14. **32-hex swarm ids need a 48-byte buffer**; 31 usable chars truncated every id and every pick
    missed.
15. **Frame version ≠ vocabulary version**: the envelope byte stays 1 unless the envelope changes;
    `proto` in `hello`/`welcome` carries vocabulary (currently 3).

## 11. Limits cheat sheet (device side)

| Limit | Value |
|---|---|
| frame payload | ≤ 8192 B |
| JSON message | < 2048 B (`JSON_MAX`; 0 or ≥ 2048 B payloads are counted `bad` and dropped) |
| agents held | 16 (`CABLE_MAX_AGENTS`) |
| machines held | 10 (`CABLE_MAX_MACHINES`) |
| swarms held | 24 (`SWARMS_MAX`) |
| notif rows | 8 |
| questions per screen | 4 (`Q_MAX`), ≤ 6 options each (`OPT_MAX`) |
| id / name lengths | `ID_MAX` 48, `NAME_MAX` 40, engine 12, model 24, effort 16, model profile id 192, notif summary 100 |
| PCM chunk | ≤ 1024 B per 0x02 frame |
| LOG line | ≤ 512 B, truncated not split |
| voice length (daemon cap) | ≈ 10 min @ 32 KB/s |
| device TX/RX buffers | TX 2048 B, RX 32768 B (32 KB) |
| models.list wait | 4000 ms, off the LVGL task |
| voice routing overlay | 60000 ms watchdog |

## 12. Compatibility & versioning

- Frame `version` byte: 1. Unknown FRAME TYPES are handed up, not dropped.
- Vocabulary `proto`: 3. Devices must ignore unknown `t` values (counted, never fatal). Daemons must
  tolerate missing optional fields; devices must tolerate missing fields and use documented
  fallbacks (`machineId`/`machine` → `""`, `panes` → `agents`, `sr` → 16000, `quiet`/`silent`/
  `restore` → false, `selected` → `welcome.machine.id`).
- Only ONE blocking round trip exists (`models.list`). Everything else is fire-and-forget plus
  unsolicited pushes; "say nothing when nothing changed" is what keeps the link idle during a long
  turn (daemon diff-keys every pushed list).
